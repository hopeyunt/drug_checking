# DrugCheck

Сервис проверки лекарственных взаимодействий для врачей.

Врач вводит список препаратов пациента — система за секунды проверяет все пары на взаимодействия и классифицирует тяжесть: от лёгкого (mild) до противопоказанного (contraindicated). База взаимодействий построена на официальных FDA-инструкциях (openFDA).

---

## Зачем это нужно

При 5 препаратах у пациента нужно проверить 10 пар взаимодействий, при 10 препаратах — уже 45. Вручную это нереально за время приёма. Особенно когда пациент приходит с назначениями сразу от кардиолога, эндокринолога и невролога.

## Как запустить

**Требования:** Docker, Docker Compose

```bash
# 1. Клонировать репозиторий
git clone https://github.com/hopeyunt/drug_checking.git
cd drug_checking

# 2. Создать .env из примера
cp .env.example .env

# 3. Запустить всё
docker compose up -d
```

Что поднимается:
- `http://localhost:8000/docs` — Swagger с API
- `http://localhost:8501` — дашборд
- `http://localhost:3000` — Grafana (логин admin / admin)
- `http://localhost:9090` — Prometheus

ML-модель обучается автоматически при первом запуске (`ml-init` сервис). Первый старт занимает 1–2 минуты.

**Создать администратора** (после первого запуска):
```bash
make create-admin
# Создаёт admin@drugcheck.ru / admin1234
# Или с другими данными:
# ADMIN_EMAIL=you@mail.ru ADMIN_PASSWORD=secret make create-admin
```

```
клиент (Streamlit)
       │
       ▼
FastAPI (REST API)
       │
       ├── PostgreSQL — пользователи, пациенты, история
       ├── Redis — очередь задач
       └── Celery Worker — асинхронная проверка взаимодействий
                │
```

Проверка взаимодействий работает асинхронно: POST /interactions/check возвращает id задачи, результат забирается через GET /interactions/check/{id}. Это позволяет не держать соединение открытым.

## ML-модель

**Классификатор:** GradientBoostingClassifier

**Данные:** официальные инструкции по применению препаратов из openFDA API — 402 уникальные пары, собранные скриптом `ml/collect_real_data.py`.

**Признаки (10 штук):**
- Фармакологические классы обоих препаратов
- CYP-ингибирование / индукция (метаболические взаимодействия)
- QT-риск, риск кровотечений, нефротоксичность
- Серотониновый синдром, узкий терапевтический индекс, одинаковый класс

**Классы тяжести:**
- `none` — нет взаимодействия
- `mild` — лёгкое, мониторинг не нужен
- `moderate` — умеренное, рекомендуется мониторинг
- `severe` — серьёзное, нужна коррекция доз
- `contraindicated` — совместный приём противопоказан

Переобучить модель на новых данных: `docker compose exec api python /ml/train.py`

## Биллинг

Реализован **Вариант Б (Продвинутый)** из технического задания — динамические скидки и уровни лояльности.

Freemium-модель с кредитной системой:
- При регистрации начисляется 50 кредитов
- Одна проверка стоит 5 кредитов (с учётом скидки по уровню)

**Программа лояльности** (пересчёт раз в месяц через Celery Beat):

| Уровень | Проверок за месяц | Скидка |
|---|---|---|
| Bronze | < 50 | 0% |
| Silver | 50–199 | 5% |
| Gold | ≥ 200 | 15% |

Параметры уровней хранятся в таблице `loyalty_config` и управляются через admin API — без пересборки приложения.

**Атомарность операций:** списание кредитов выполняется через `SELECT ... FOR UPDATE` — строка пользователя блокируется на время транзакции, гонки при параллельных запросах исключены.

Оплата через ЮКасса. Без ключей в .env работает в тестовом режиме — кредиты начисляются без реальной оплаты.

## Этапы реализации и технические решения

### 1. Проектирование и схема БД
Первым делом спроектировала схему данных. Ключевой вопрос был — как хранить уровни лояльности: хардкодом в коде или в БД. Выбрала таблицу `loyalty_config`, потому что бриф явно предупреждал: правила скидок должны меняться через admin API без пересборки. Это усложнило модели, но сделало систему управляемой.

### 2. Аутентификация и роли
Реализовала JWT с двумя ролями: `user` и `admin`. Столкнулась с проблемой: при асинхронных запросах к БД нельзя использовать стандартный sync-драйвер. Перешла на `asyncpg` + SQLAlchemy async — это потребовало переписать все сессии и изучить `AsyncSession`.

### 3. ML-интеграция
Самостоятельно собрала датасет из openFDA API (`collect_real_data.py`) — 402 реальные пары препаратов с описанием взаимодействий. Вручную разметила тяжесть (none / mild / moderate / severe / contraindicated) по тексту инструкций. Обучила `GradientBoostingClassifier` на 10 признаках (фармакологические классы, CYP-ингибирование, QT-риск и др.).

Предсказание сделала асинхронным через Celery: POST возвращает `task_id`, результат забирается через GET. Это решает проблему таймаутов при медленных моделях и позволяет масштабировать воркеры независимо от API.

### 4. Биллинг и атомарность
Главная сложность — race condition при параллельных списаниях. Если два запроса одновременно читают баланс, оба могут пройти проверку, а баланс уйдёт в минус. Решение: `SELECT ... FOR UPDATE` — строка пользователя блокируется на время транзакции. Протестировала на параллельных запросах.

### 5. Программа лояльности (Вариант Б)
Реализовала фоновый Celery Beat: 1-го числа каждого месяца пересчитывается уровень всех пользователей на основе `monthly_checks`. Уровни и пороги хранятся в `loyalty_config` — можно менять через admin API.

### 6. Мониторинг
Подключила Prometheus через `prometheus-fastapi-instrumentator` — он автоматически экспортирует метрики всех эндпоинтов. В Grafana настроила дашборд: RPS, latency по перцентилям, количество активных задач Celery.

### 7. Тестирование
Писала тесты параллельно с кодом. Самое сложное — изолировать тесты биллинга: нужно было мокировать и YooKassa, и Celery, и БД одновременно. В итоге сделала отдельную тестовую БД (`drugcheck_test`) и фикстуры с автоматическим откатом транзакций после каждого теста.
